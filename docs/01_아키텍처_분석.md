## 1. RNA/DNA 데이터 모델 — "파일이 자기 자신을 설명한다"

### 설계 원리
블렌더는 데이터 정의를 **DNA**와 **RNA** 두 층으로 분리한다.

- **DNA**: `.blend` 파일에 저장되는 저수준 구조체 정의. 컴파일 시 `makesdna`라는 프로그램이
  C 헤더의 struct 정의를 파싱해서 **SDNA**(Structure DNA, 모든 구조체의 이진 스키마
  기술서)를 만든다. **이 SDNA 자체가 저장될 때마다 `.blend` 파일 안에 통째로 함께
  저장된다.** 즉 파일 하나하나가 "이 파일이 어떤 구조로 이뤄져 있는지"를 자체적으로
  포함하는 자기 기술적(self-describing) 포맷이다.
- **RNA**: DNA 위에 얹힌 런타임 프로퍼티 접근 계층. `bpy.types`, `bpy.props`로 노출되는
  모든 속성이 여기서 나온다. 파이썬 API, UI 패널, 파일 포맷이 전부 **같은 RNA 정의
  하나**에서 자동으로 파생된다 — 속성을 하나 등록하면 UI 위젯, `bpy.ops`/`bpy.data` API,
  `.blend` 저장/로드, 실행취소(undo)까지 전부 공짜로 따라온다.

### 실제 코드 근거
`E:\4.3\scripts\startup\bl_operators\object_randomize_transform.py`의
`RandomizeLocRotSize` 오퍼레이터: `random_seed: IntProperty(...)`, `loc: FloatVectorProperty(...)`
같은 선언 몇 줄이 (a) 오퍼레이터 재실행 패널(F9) UI, (b)
`bpy.ops.object.randomize_transform(random_seed=0, loc=(0,0,0), ...)` 파이썬 호출 시그니처,
(c) undo 스택 항목을 **동시에** 만들어낸다. 스키마를 한 번만 적으면 세 가지 표면이 자동
생성되는 구조를 코드 레벨에서 직접 확인.

### 왜 강력한가
버전 호환성 문제를 "저장 시점에 파일이 스스로 설명서를 들고 다니게" 만들어서 해결한다.
로드 시점에 `blenloader/intern/versioning_*.cc`의 마이그레이션 함수가 옛 SDNA를 새 구조로
변환하는데, 이 변환 로직은 코드 안에 있어서 **고치고 확장하고 나중에 지울 수 있다** — 파일
자체에 하드코딩되는 게 아니다. 대부분의 게임 엔진/에셋 포맷(예: 커스텀 바이너리 포맷)은
외부 버전 번호 + 하드코딩된 파서로 호환성을 처리하는데, 블렌더는 스키마 자체를 파일에
동봉하는 좀 더 근본적인 해법을 쓴다.

### 응용 착안점
자체 툴(예: MIRIM 프로젝트의 캐릭터 데이터/설정 저장 포맷, 또는 향후 만들 에디터)에서
"설정 스키마 변경 → 옛 저장 파일 깨짐" 문제가 반복된다면, RNA처럼 **속성 정의를 UI·API·
직렬화가 공유하는 단일 소스**로 두고, 저장 시 그 스키마 버전 메타데이터를 파일에 함께
기록하는 방식을 도입할 수 있다. 매번 "이 필드가 언제 추가됐는지"를 코드 여기저기 흩어
관리하는 대신, 로드 시점의 버저닝 함수 한 곳에 모아두는 패턴만 가져와도 유지보수 부담이
크게 줄어든다.

### 코드 레벨 검증 (2026-09-05 추가)
작성 당시엔 C++ 코어 소스를 못 구해서 공식 문서로만 보강했는데, VirtualBox 분석([[02번
문서]])에서 쓴 방식 그대로 공식 GitHub(`blender/blender`)에서 실제 구현
(`source/blender/makesdna/intern/dna_genfile.cc`)을 받아 확인했다.

핵심은 필드별 변환을 **인스턴스마다 다시 계산하지 않고, 구조체 타입 하나당 딱 한 번만
"변환 명령 리스트"로 컴파일**해두는 것이다 (`DNA_reconstruct_info_create`가 미리 계산).
실제 실행부(`reconstruct_struct`)는 이 명령 리스트를 그냥 순서대로 재생만 한다:

```c++
switch (step->type) {
  case RECONSTRUCT_STEP_MEMCPY:            // 필드 그대로 복사
  case RECONSTRUCT_STEP_CAST_PRIMITIVE:    // 타입 변경(int→float 등) 캐스팅
  case RECONSTRUCT_STEP_CAST_POINTER_TO_32: // 64비트 포인터 → 32비트로 축소
  case RECONSTRUCT_STEP_CAST_POINTER_TO_64: // 32비트 포인터 → 64비트로 확장
  case RECONSTRUCT_STEP_SUBSTRUCT:         // 중첩 구조체는 재귀적으로 같은 처리
  case RECONSTRUCT_STEP_INIT_ZERO:         // 새로 추가된 필드는 0으로 (이미 zeroed 메모리)
}
```

파일 하나에 같은 타입 오브젝트가 수만 개 들어있어도(메시 정점 등) 필드 매핑 자체는
"타입당 1회"만 풀이하고, 그 결과(오프셋/타입 목록)를 인스턴스 수만 번 재사용한다 —
심지어 **32비트로 저장된 옛 `.blend` 파일을 64비트 빌드가 포인터 크기까지 자동 보정해서
읽는 것**까지 이 메커니즘 하나로 처리된다.

이건 "다수의 인스턴스를 옛 스키마→새 스키마로 마이그레이션해야 할 때, 인스턴스마다
필드 이름을 다시 비교하지 말고 그 비교 결과를 명령 리스트로 미리 컴파일해서 재생만
하라"는, 원래 응용 착안점보다 한 단계 더 구체적인 성능 패턴이다 — 마이그레이션 로직이
"어떻게 변환할지 결정"과 "실제로 변환 실행"으로 분리돼 있다는 뜻이기도 하다.

## 2. Operator 패턴 — 모든 동작이 "선언 가능한 명령"이다

### 설계 원리
블렌더에서 사용자가 하는 거의 모든 동작(오브젝트 이동, 메시 편집, 렌더링 시작)은
`bpy.types.Operator`를 상속한 클래스 하나로 표현된다. 생명주기는 4단계:

- `poll(cls, context)` — 지금 이 컨텍스트에서 실행 가능한가(버튼 활성/비활성 여부 결정).
- `invoke(self, context, event)` — 처음 트리거될 때(마우스 클릭 등 이벤트 정보 필요할 때).
- `execute(self, context)` — 실제 동작 수행, 즉시 실행형 오퍼레이터의 본체.
- `modal(self, context, event)` — 마우스 드래그처럼 여러 프레임에 걸쳐 이벤트를 계속
  받아야 하는 상호작용형 오퍼레이터.

`bl_options`(`{'REGISTER', 'UNDO', 'GRAB_CURSOR', 'BLOCKING', 'INTERNAL'}` 등) 플래그
조합으로 "이 오퍼레이터가 실행취소 스택에 들어가는가", "마우스 커서를 가두는가" 같은
런타임 동작이 선언적으로 결정된다.

### 실제 코드 근거
`E:\4.3\scripts\startup\bl_operators\wm.py`의 `WM_OT_context_modal_mouse`: 마우스 이동으로
임의의 수치 속성을 조정하는 범용 오퍼레이터. `_values_store/_values_delta/_values_restore`로
modal 상태를 관리하고, `bl_options = {'GRAB_CURSOR', 'BLOCKING', 'UNDO', 'INTERNAL'}`로
"드래그 중 커서 고정 + 완료 시 undo 등록"을 선언 한 줄로 처리. 노드 추가조차
`node.add_node`라는 **범용 오퍼레이터**에 `type` 프로퍼티로 어떤 노드인지 넘기는 방식이라
(`nodeitems_utils.py`의 `NodeItem.draw`에서 확인), "N개 기능 = N개 특수 API"가 아니라
"모든 기능이 같은 오퍼레이터 인터페이스를 통과"하는 구조다.

### 왜 강력한가
UI 버튼, 단축키, 파이썬 스크립트, 매크로 녹화(사용자 액션 재생)가 전부 **같은 오퍼레이터
호출**을 거치기 때문에, 새 기능을 하나 추가하면 그 네 가지 진입점에 자동으로 다 연결된다.
실행취소도 오퍼레이터 단위로 통일 관리되므로 "이 동작은 undo가 되는데 저 동작은 안 된다"는
불일치가 구조적으로 적게 발생한다.

### 응용 착안점
게임 엔진 에디터 툴이나 자체 파이프라인 툴을 만들 때, "버튼 클릭"과 "스크립트 호출"과
"매크로 재생"을 각각 따로 구현하지 말고, 하나의 `Command` 인터페이스(poll/execute + 옵션
플래그로 undo 등록 여부)로 통일하면 나중에 배치 자동화(예: 여러 캐릭터에 같은 편집을 일괄
적용)를 붙이기가 훨씬 쉬워진다. 특히 향후 "휴대폰 원격 요청으로 툴을 대신 실행" 같은 걸
만들 계획이 있다면(오늘 대화에서 언급됨), 모든 동작을 이런 poll/execute 단일 인터페이스로
통일해두는 게 원격 트리거 설계를 훨씬 단순하게 만든다.

## 3. 노드 기반 시스템 — "노드 타입은 C, 메뉴는 Python, 실행은 컴파일된 그래프"

### 설계 원리
Shader Nodes/Geometry Nodes/Compositor의 실제 노드 타입(`ShaderNodeXXX` 등)은 C++
RNA 서브클래스로 정의돼 있어 로컬 Python 소스에는 없다. 하지만 **어떤 노드를 메뉴 어디에
보여줄지 분류하는 계층은 순수 Python**이다(`E:\4.3\scripts\modules\nodeitems_utils.py`의
`NodeCategory`/`NodeItem`). 즉 "노드가 뭘 하는가"(C++ 코어, 성능 critical)와 "사용자가
어떻게 노드를 찾고 추가하는가"(Python, UI/UX 실험이 잦은 영역)가 명확히 분리돼 있다.

Geometry Nodes의 실제 실행 엔진은 최근 몇 년간 크게 재설계됐다: 사용자가 짠 노드 그래프를
그대로 인터프리트하지 않고, **"lazy-function graph"라는 내부 중간 표현(IR)으로 컴파일한
뒤** 그 IR을 평가한다. 필요한 데이터만 그때그때 계산하는 지연 평가이고("어떤 데이터가
필요한지"를 실행 중에 동적으로 결정), 여기에 **Field**라는 개념이 얹힌다 — Field는
"버텍스/면 등 도메인 전체에 걸쳐 지연 계산되는 값"으로, 넘파이의 브로드캐스팅이나 셰이더의
varying 변수와 비슷하게 "한 번 정의하고 여러 요소에 암묵적으로 벡터화 적용"되는 계산
단위다. 이 재설계 이후 반복(iteration) 인덱스별로 서로 다른 스레드에서 병렬 평가가
가능해져 실측 800ms→70ms급 개선 사례가 보고됨.

### 응용 착안점
언리얼 블루프린트류 비주얼 스크립팅을 자체적으로 만들 일이 생기면, "노드 그래프를 매번
인터프리트"하는 대신 **한 번 컴파일해서 재사용 가능한 실행 그래프(IR)로 캐싱**하는 접근이
훨씬 유리하다는 게 실측으로 증명된 셈이다. 또한 Field 개념 — "이 계산은 개별 값이 아니라
도메인 전체에 지연 적용되는 함수"라는 추상화 — 는 절차적 캐릭터 커스터마이징(예: 여러
캐릭터의 파츠에 같은 변형 로직을 일괄 적용) 파이프라인을 설계할 때 그대로 가져다 쓸 수
있는 패턴이다: "이 표정 강도 값을 캐릭터 개별로 하드코딩"하지 않고 "얼굴의 모든 버텍스
도메인에 지연 적용되는 필드"로 표현하면, 나중에 다른 메시/다른 캐릭터에도 로직 재작성 없이
재사용 가능해진다.

### 코드 레벨 검증 (2026-09-05 추가)
`source/blender/functions/FN_lazy_function.hh`/`FN_field.hh`를 실제로 확인하니, 원래
서술("지연 평가")보다 훨씬 구체적인 메커니즘이었다.

**LazyFunction은 사실상 "재진입 가능한 상태 기계(코루틴)"다.** 헤더 주석이 든 예시가
정확히 Geometry Nodes의 Switch 노드인데, 한 노드 실행이 **여러 번에 걸쳐 호출**된다:
1. 1차 호출: 출력이 필요하다는 걸 알고, "조건 입력값부터 달라"고 요청하며 종료
2. 2차 호출: 조건값을 받아서, **두 갈래 입력 중 실제로 필요한 것 딱 하나만** 요청
3. 3차 호출: 그 값을 받아 출력으로 넘기고 종료

즉 "쓸모없는 쪽 브랜치는 아예 그 서브그래프 전체가 계산되지 않는다" — 이게 중첩된
노드 그룹을 넘어서도 유지된다(주석: "노드 그룹 안의 Switch가 부모 그룹의 노드를 실행할지
말지도 결정할 수 있어야 한다"). 단순히 "위상정렬 후 필요한 노드만 평가"하는 게 아니라,
**노드 하나의 실행 자체를 여러 스텝으로 쪼개서 "지금 뭐가 더 필요한지"를 실행 도중에
되묻는 콜링 컨벤션**으로 구현돼 있다.

`FN_field.hh`의 Field는 트리 구조로 저장되다가 평가 시점에 `multi-function procedure`로
변환되는데, 주석에 "여러 Field가 같은 서브 Field/컨텍스트를 공유하면 **함께 평가해서
중복 계산을 피해야 한다**"고 명시돼 있다 — 여러 출력이 같은 하위 계산(예: "가장 가까운
점까지 거리")에 의존하면 공통 부분식 제거(CSE)처럼 한 번만 계산해서 공유한다.

### 응용 착안점 (추가)
언리얼 블루프린트류를 직접 만든다면, "필요한 노드만 골라 평가"를 넘어서 **노드 실행
자체를 재진입 가능하게 설계**하면 조건 분기(if/switch류) 노드에서 안 쓰는 브랜치의
서브그래프를 통째로 건너뛸 수 있다 — 이건 상위 그래프 실행 전체를 멈추고 되묻는 방식이라,
"평가 순서를 미리 다 계산해두는" 방식보다 실제 실행되는 연산량 자체가 줄어든다. 여러
캐릭터/여러 출력이 같은 중간 계산(거리장, 노이즈 등)을 공유한다면 Field처럼 "동시에
요청된 것들을 묶어서 공통 부분만 한 번 계산"하는 최적화도 그대로 가져올 만하다.

## 4. Dependency Graph(의존성 그래프) — 컴포넌트 단위 병렬 평가 + Copy-on-Write

### 설계 원리
블렌더 2.8부터 의존성 그래프는 **오브젝트 단위가 아니라 컴포넌트 단위**로 세분화됐다 —
한 오브젝트의 Transform, Mesh 데이터, Armature(뼈대)가 그래프 안에서 각각 별개의 노드로
취급된다. 그래서 오브젝트 위치만 옮기면, 그 오브젝트에 걸린 복잡한 디폼 모디파이어를 다시
계산할 필요가 없다(둘이 그래프상 직접 연결돼 있지 않다면).

평가는 두 단계로 나뉜다: (1) 태그가 붙은 변경 사항을 그래프 관계를 따라 하위로 전파(flush),
(2) 입력이 모두 준비된 연산들을 멀티스레드로 동시 실행 — 한 연산이 끝나면 그 자식 중
의존성이 다 채워진 것들이 다음 실행 대상으로 스케줄된다(태스크 그래프 스케줄링과 동일한
패턴). 그리고 평가는 항상 **원본 데이터의 복사본(Copy-on-Write)** 위에서 일어나서, 뷰포트나
렌더링이 평가된 사본을 갖고 작업하는 동안 원본이 오염되지 않고, 독립된 그래프 가지들을
안전하게 병렬 처리할 수 있다.

### 코드 레벨 검증 (2026-09-05 추가)
`source/blender/depsgraph/intern/node/deg_node.hh`의 `NodeType` enum에 실제로
`ANIMATION`, `TRANSFORM`, `GEOMETRY`, `EVAL_POSE` 같은 값이 있어서 "컴포넌트 단위로
쪼갠다"는 주장이 코드로 확인됐다. 더 흥미로운 건 `deg_eval_copy_on_write.cc`인데,
**이름과 달리 실제로는 OS 수준의 지연(lazy) Copy-on-Write가 아니다.** 평가 시작 시
`id_copy_inplace_no_main()`이 `BKE_id_copy_ex()`를 호출해서 **즉시(eager) 전체
복사**를 만든다:
```c++
BKE_id_copy_ex(nullptr, id_for_copy, &newid,
    LIB_ID_COPY_LOCALIZE |       // Main 데이터베이스에 등록 안 함 — UI/실행취소에서 안 보임
    LIB_ID_CREATE_NO_ALLOCATE |  // 새로 malloc 안 하고 이미 할당된 메모리 재사용
    LIB_ID_COPY_SET_COPIED_ON_WRITE);
```
즉 "Copy-on-Write"라는 이름은 리눅스 `fork()`처럼 실제 쓰기가 일어날 때까지 복사를
미루는 게 아니라, **"평가 전에 즉시 복사해두고, 그 복사본에만 쓴다"**는 뜻으로 붙은
이름이다(정확히는 "Copy, then Write"). 대신 메모리 재할당 오버헤드는 두 가지 플래그
(Main 미등록 + 사전할당 메모리 재사용)로 줄여서, 매 프레임 반복되는 이 복사 비용을
낮춘다.

### 응용 착안점
NVIDIA ACE류 실시간 캐릭터 시스템(표정/립싱크/애니메이션이 매 프레임 갱신되는 시스템)을
직접 설계하게 된다면, "캐릭터 전체를 매 프레임 통으로 재계산"하는 대신 이 컴포넌트 단위
그래프 분리 원칙을 가져와 "표정만 바뀌면 표정 컴포넌트만, 뼈대만 바뀌면 뼈대 컴포넌트만"
재평가하도록 설계하면 실시간 성능 확보에 직결된다. Copy-on-Write 원칙도 유용하다 — 여러
스레드/여러 시스템(렌더링, 물리, AI)이 캐릭터 상태를 동시에 읽고 쓰려 할 때, "평가용 사본에서
작업하고 확정된 결과만 원본에 반영"하는 구조는 락(lock) 경합을 줄이는 검증된 해법이다.

## 6. Python API 레이어링 — `bpy`(RNA) / `bmesh`(편집용 자료구조) / `mathutils`(경량 수학)

### 설계 원리
- **`bpy`**: RNA에서 자동 생성된 전체 데이터 모델 API. 저장되는 `Mesh` 등 모든 데이터
  타입을 다루지만, 저장 포맷에 최적화된 구조라 실시간 편집(정점 하나씩 잘라내기/합치기
  등)에는 비효율적이다.
- **`bmesh`**: 메시 편집 전용 반쪽 자료구조(half-edge 기반) — 저장용 `Mesh`와는 완전히
  다른, 편집 연산(익스트루드, 베벨, 루프컷)에 최적화된 임시 구조. 편집 끝나면 다시 `Mesh`로
  변환해서 저장한다.
- **`mathutils`**: Vector/Matrix/Quaternion 등 벡터 수학만 담당하는 가벼운 C 확장 모듈 —
  RNA 시스템과 무관하게 독립적으로 동작.

즉 "저장을 위한 자료구조"와 "편집을 위한 자료구조"와 "순수 수학 유틸리티"를 의도적으로
분리해서, 저장 포맷을 편집 성능에 맞춰 타협하지도 않고 편집 성능을 저장 포맷 제약에 맞춰
타협하지도 않는다.

리깅 쪽은 코어 API 위에 **Rigify**(번들 애드온, `E:\4.3\scripts\addons_core\rigify\`)가
좋은 응용 사례를 보여준다: 사용자는 단순한 "메타리그"(뼈대 배치 + 각 뼈에 태그만 지정)만
만들고, `Rig` 클래스들이 `find_org_bones → initialize → generate_bones → parent_bones → ...`
같은 **다단계 파이프라인(멀티패스 컴파일러 구조)**을 거쳐 실제 컨트롤/디폼 뼈대와
컨스트레인트를 자동 생성한다(`E:\4.3\scripts\addons_core\rigify\rigs\basic\super_copy.py`에서
실제 단계별 메서드 확인). 이건 "리깅 담당자가 손으로 컨스트레인트를 일일이 배치"하는 언리얼
Control Rig/유니티 Animation Rigging의 일반적 워크플로우와 달리, **선언적 메타데이터 →
멀티패스 생성기가 프로덕션 리그를 컴파일**하는 방식이다.

### 응용 착안점
1. 저장/편집/수학을 하나의 만능 자료구조로 퉁치지 말고 목적별로 분리하는 원칙은, 캐릭터
   데이터를 다룰 자체 파이프라인(예: MIRIM 캐릭터 시트 → 3D 모델 → 리그)에서도 "저장용
   포맷"과 "실시간 편집용 임시 구조"를 구분해서 설계하면 나중에 편집 성능 문제를 겪을
   확률이 줄어든다.
2. Rigify식 "메타데이터 선언 + 멀티패스 생성기" 패턴은, 캐릭터마다 리그를 매번 손으로 짜는
   대신 **뼈대 역할 태그만 지정하면 표준 리그가 자동 생성되는 도구**를 자체 제작할 때 그대로
   참고할 청사진이 된다 — 언리얼/유니티에도 이 정도로 성숙한 "리그 컴파일러"는 표준
   제공되지 않으므로, 이 부분은 블렌더 생태계가 실질적으로 앞서 있는 지점이다.

   코드 검증: 블렌더의 "Copy-on-Write"는 실제로는 지연복사가 아니라 평가 직전 즉시
   전체복사 — 이름에 속지 말고 "복사 시점"과 "복사 비용 절감 방법"을 구분해서 설계할 것.)
5. **매니페스트 기반 권한 선언**: 자체 확장/플러그인 생태계를 만들 때 "이 확장이 뭘
   할 수 있는가"를 코드 속에 숨기지 않고 매니페스트에 명시 — 오늘 정리한 행동별 권한
   분류 원칙과 같은 결이므로 도구화하기 좋음. (2026-09-05 코드 검증: 블렌더 자신도
   "업데이트 시 권한 상승 재확인"은 TODO로 미해결 — 직접 만들 때는 설치 시점뿐 아니라
   업데이트 시점의 권한 diff 재확인까지 처음부터 설계에 넣을 것.)
6. **저장/편집/수학 자료구조 분리**: 캐릭터 데이터 파이프라인을 만들 때 저장 포맷,
   실시간 편집용 임시 구조, 순수 수학 유틸을 처음부터 분리 설계.
7. **선언적 메타데이터 + 멀티패스 생성기(Rigify 패턴)**: 캐릭터별 리그를 매번 손으로
   짜지 않고, 뼈대 역할 태그 → 멀티패스 생성기가 표준 리그를 컴파일하는 자체 도구를
   만들면 언리얼/유니티보다 앞선 지점을 확보할 수 있음 — 가장 우선순위 높은 응용 후보.
